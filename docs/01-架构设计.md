# 01 · 架构设计

> 状态：设计稿。**尚未在鸿蒙真机上验证任何一条链路。**
> 证据标记约定见 [`AGENT.md`](../AGENT.md) 第 8 节。

---

## 1. 设计目标与非目标

**目标**
- 复刻 v2rayN 的**使用模型**：订阅导入 → 节点管理 → 规则分流 → 一键连接 → 流量/日志可见。
- 全原生：ArkTS 前端 + 原生内核，无 WebView、无 Electron、无套壳。
- 平台能力用系统正式 API（`VpnExtensionAbility`），不依赖 root、不依赖私有接口。
- 依赖面尽量小：只依赖 `@kit.*` SDK。

**非目标（本阶段）**
- 不做 Windows/Linux/macOS 端；不做全局透明代理之外的高级企业功能（除非 `ENTERPRISE_VPN` 路线的合规评估支持）。
- 不做第三方内核插件市场。
- 不承诺兼容 v2rayN 的全部协议与传输组合（首版按第 5 节的能力子集推进）。

## 2. 分层架构

```
┌─────────────────────────── 应用进程（主 HAP） ───────────────────────────┐
│                                                                          │
│  pages/            Index(连接) / Nodes / Subscriptions / Settings / Logs  │
│      │                    纯 UI，不含业务逻辑                             │
│      ▼                                                                   │
│  viewmodel/        @ObservedV2 + @Trace 状态机，暴露意图方法              │
│      │                                                                   │
│      ▼                                                                   │
│  service/          订阅解析、节点校验、配置生成（纯逻辑，可单测）          │
│      │                                                                   │
│      ▼                                                                   │
│  core/Bridge.ets   ★ 唯一允许触碰原生的层（可 mock）                      │
│      │                                                                   │
│      │  ① 生成 config.json → 应用 files 目录                             │
│      │  ② vpnExtension.startVpnExtensionAbility(want)                    │
│      ▼                                                                   │
│  connectServiceExtensionAbility(want.parameters = {                      │
│      VPN_CONFIG, ASSET_LOCATION, CONFIG_LOCATION })                      │
│      │                                                                   │
│      │  ③ 订阅 commonEvent 'VPN_TRAFFIC' 拿流量                          │
└──────┼───────────────────────────────────────────────────────────────────┘
       │  IPC（系统）
┌──────▼───────────────── VPN 扩展进程（独立进程） ──────────────────────┐
│  vpnability/VpnAbility.ets   extends VpnExtensionAbility                │
│      onCreate(want) → vpnExtension.createVpnConnection(this.context)      │
│                     → connection.create(VpnConfig) ⇒ vNIC fd             │
│                     → fd 交给 tun2socks（**不是 Xray**）                  │
│                     → Bridge.startCore({fd, assetLocation, configLocation})│
│      每秒轮询         statistics.getIface[Tx|Rx]Bytes('vpn-tun')          │
│                     → commonEventManager.publish('VPN_TRAFFIC', {...})   │
│      onDisconnected → connection.destroy()                              │
│      onDestroy      → process.ProcessManager().exit(0)                   │
└──────┬───────────────────────────────────────────────────────────────────┘
       │
┌──────▼────────────────────── 原生内核 ──────────────────────────────────┐
│  libbridge.so  (NAPI C++)   dlopen("libcore.so") + dlsym("GoInvoke")     │
│      └─ libcore.so  (Go c-shared / Xray-core)                            │
│            监听本地 socks/http 入站 ⇒ 按 config.json 的 routing 出站       │
│            ⚠️ 不接管 tun：vNIC fd 交给 tun2socks（见 ipc-contract §2）      │
└─────────────────────────────────────────────────────────────────────────┘
```

**关键事实**：VPN 扩展运行在**独立进程**，内核也因此在那个进程里。
主进程只能通过 **公共事件** 拿到流量与状态，不能直接读内核内存。这是本架构最重要的一条约束，
它决定了"连接状态"必须是**最终一致的**（主进程的状态是对扩展进程的观察，不是权威）。

## 3. 端到端调用链（控制流）

### 3.1 建立连接

```
用户点"连接"
 └─ viewmodel.connect()
     ├─ Bridge.generateConfig(...) → core/config.json 写入应用 files 目录
     └─ Bridge.connectVpn(context, configPath, assetPath)
         └─ vpnExtension.startVpnExtensionAbility({bundleName, abilityName:'VpnAbility'})
             │   ← 系统弹出用户授权对话框
             │   授权结果可由 vpnExtension.createVpnObserver().onAuthorizationResult() 获取（@since 26.0.0）
             ▼
         context.connectServiceExtensionAbility(want{parameters}, {onConnect,onDisconnect,onFailed})
             ▼  [VPN 扩展进程]  ← 只能依赖 onCreate / onDestroy
         VpnExtensionAbility.onCreate(want)
             ├─ createVpnConnection(this.context)
             ├─ connection.create(want.parameters.VPN_CONFIG) ⇒ vNIC fd
             ├─ 把 fd 交给 tun2socks（**不是交给 Xray**，见 ipc-contract §2）
             ├─ Bridge.startCore({configLocation, assetLocation, start:true})
             │     → Xray 起来后监听本地 socks/http 入站
             ├─ 启动每秒统计轮询（statistics.getIface*Bytes('vpn-tun')）
             │     → commonEventManager.publish('VPN_TRAFFIC', {...})
             ▼  [主进程]
         onConnect 回调 → viewmodel.status = Connected
```

> ⚠️ **必须知道的 API 事实（已实测）**：本机 SDK 的 `@ohos.app.ability.VpnExtensionAbility.d.ts`
> **只声明 `onCreate` / `onDestroy`**，全 SDK 搜索**没有** `onConnect` / `onDisconnected`。
> 网传的"标准生命周期"**不是公开契约** —— x4h 用了它（说明运行时可能有），但 Hey 没用。
> **本项目只在 `onCreate` 里自驱动**，不依赖未文档化回调。
> 另注：`onRequest` 也未声明，但 Hey 能用 → 该工程未开 `typeCheck`，**"能编译" ≠ "API 存在"**。

### 3.2 断开

```
用户点"断开"
 └─ Bridge.disconnectVpn(context, connectionId)
     ├─ context.disconnectServiceExtensionAbility(connectionId)
     └─ vpnExtension.stopVpnExtensionAbility(want)
         ▼  [VPN 扩展进程]
         onDestroy → connection.destroy()             ← 系统撤销虚拟网卡
                   → process.ProcessManager().exit(0)  ← 结束整个扩展进程（连带内核）
```

> 因为扩展进程会被整体 `exit(0)`，内核**不能**假设自己可以跨连接复用；每次连接都是全新的内核实例。
> 这也意味着"连接状态"在主进程里只能是对扩展进程的**观察**，不是权威 —— 状态机会因此是最终一致的。

## 4. 模块职责与边界

| 模块 | 路径 | 职责 | 绝对不做的事 |
|---|---|---|---|
| 页面 | `entry/src/main/ets/pages/` | 布局、交互、导航 | 不写业务逻辑、不碰原生 |
| ViewModel | `entry/src/main/ets/viewmodel/` | 状态机、意图、跨页存活 | 不直接调原生 |
| 服务 | `entry/src/main/ets/service/` | 订阅解析、节点校验、配置生成 | 不含 UI、不碰原生 |
| **Bridge** | `entry/src/main/ets/core/Bridge.ets` | **唯一**原生出入口，类型安全包装 | 不含业务规则 |
| 模型 | `entry/src/main/ets/model/` | 共享类型/枚举 | 无逻辑 |
| VPN 扩展 | `entry/src/main/ets/vpnability/` | 建立 vNIC、启动内核、上报流量 | 不做 UI |
| NAPI 桥 | `entry/src/main/cpp/` | C ABI ↔ NAPI 转换、`dlopen` | 不含业务逻辑 |
| 内核包装 | `entry/src/main/golang/` | Xray-core 装配、服务分发、跨边界防崩 | 不感知 ArkTS 类型 |

**分层铁律**：任何"UI 里直接读 config 文件""ViewModel 里直接 `dlopen`"的写法都是缺陷。

## 5. 原生接口契约（ABI）

### 5.1 C ABI（Go ↔ C++）

```c
char* GoInvoke(const char* service, const char* parameters);  // 返回 heap 字符串，JSON 信封
void  GoFreeCString(char* result);                            // 必须调用以释放
```

### 5.2 NAPI 导出（C++ ↔ ArkTS）

```ts
// entry/src/main/cpp/types/libbridge/Index.d.ts
export const Invoke: (service: string, paramsJson: string) => string;
```

### 5.3 信封格式

```json
{ "success": true,  "result": { }, "error": "" }
{ "success": false, "result": null, "error": "human readable message" }
```

### 5.4 服务目录（首版）

> 下表的服务名以 `entry/src/main/golang/` 里**实际 `ipc.Register` 的名字为准**。
> 改动服务名必须同步 `golang/`、`cpp/`、`types/libbridge/Index.d.ts`、`core/Bridge.ets` 四处。

| 服务名 | 参数 | 返回 | 说明 |
|---|---|---|---|
| `CoreService.Start` | `{fd, assetLocation, configLocation}` | `{}` | 用 vNIC fd 拉起 Xray tun 入站 |
| `CoreService.Stop` | `{}` | `{}` | 停止内核 |
| `CoreService.Status` | `{}` | `{running, startedAt, ...}` | 内核运行状态 |
| `VersionService.GetVersion` | `{}` | `{version}` | 内核版本（**真机验证桥接链路的第一个调用**，无副作用） |
| `LogService.Tail` | `{limit}` | `{lines: []}` | 最近日志环形缓冲 |
| `LogService.Clear` | `{}` | `{}` | 清空日志缓冲 |
| `PingService.Tcping` | `{host, port}` | `{delayMs}` | TCP 连通延迟测量 |
| `ValidatorService.ValidateConfig` | `{configJson}` | `{valid, message}` | 配置合法性预检 |

> **契约耦合**：上述任一项变化，必须在同一提交内同步 `golang/main.go`、`cpp/`、`types/libbridge/Index.d.ts`、`core/Bridge.ets` 四处。

## 6. 数据模型（草案）

```
ServerNode   { id, name, protocol, address, port, uuid/password, transport, tls, sni, latencyMs?, raw? }
Subscription { id, name, url, lastUpdated, nodeCount, enabled }
AppSettings  { routingMode: Global|Rule|Direct, mtu, dns, sniffing, allowLan,
               perAppMode: Off|Allowlist|Blocklist, appList[], logLevel, coreVariant }
ConnectionState = Disconnected | Connecting | Connected | Disconnecting
TrafficStats { totalUp, totalDown, speedUp, speedDown }
LogEntry     { ts, level, tag, message }
```

`RoutingMode` 语义对齐 v2rayN：全局（全部走代理）/ 规则（geoip+geosite 分流）/ 直连（不走代理）。

## 7. 首版能力子集（有意收窄）

| 能力 | 首版 | 说明 |
|---|---|---|
| 协议 | VMess / VLESS / Trojan / Shadowsocks | 覆盖绝大多数订阅；Hysteria/QUIC 后续 |
| 传输 | TCP / WS / gRPC / HTTPUpgrade / TLS / Reality | 与订阅实际使用情况对齐 |
| 订阅格式 | Base64 订阅 + `vless://`/`vmess://` 等分享链接 | 先做最常见形态 |
| 分流 | geoip / geosite 规则 | 需要内置 `.dat`（~30 MB，走 LFS 或按需下载） |
| 按应用分流 | `trustedApplications` / `blockedApplications` | API ≥ 11；注意名单上限随 API 版本变化 |
| 多 VPN 并存 | 否 | `generateVpnId()` 仅 IPv4，首版不做 |

## 8. 需要真机才能定稿的设计点（当前为设计假设）

| # | 假设 | 影响 | 验证方式 |
|---|---|---|---|
| A1 | `VpnConnection.create()` 返回的 fd 可直接被 Xray tun 入站接管 | 决定整个内核接入方式 | 真机最小闭环（AGENT.md 第 9 节第 4 步） |
| A2 | 授权对话框出现时机与频率（每次连接 or 仅首次） | 决定 UX 与状态机 | 真机 + `onAuthorizationResult` |
| A3 | `protect(fd)` 对 Xray 出站 socket 生效、足以防回环 | 不做会直接断网 | 真机连通性测试 |
| A4 | `statistics.getIface*Bytes('vpn-tun')` 命名与可用性稳定 | 流量显示 | 真机读数 |
| A5 | VPN 扩展进程存活策略（前台通知/被回收行为） | 断线重连设计 | 真机长时间挂机 |
| A6 | 扩展进程内哪些 SDK 模块不可用（官方列出 contact/geo/audio/camera/telephony） | 内核能链哪些库 | 查阅并最小化依赖 |

## 9. 与 v2rayN 的对应关系

| v2rayN（Windows） | HarmonyBridge | 差异原因 |
|---|---|---|
| WPF 主窗口 + MVVM | ArkTS 页面 + `@ObservedV2` | 平台 UI 框架 |
| 独立 `xray.exe` 进程 | 同进程内 `libcore.so` | 鸿蒙不鼓励任意可执行体；c-shared 更稳 |
| 系统代理 / TUN | 仅 `VpnExtensionAbility` | 鸿蒙无 Windows 式系统代理设置 |
| 全局热键 | 不做 | 手机无此需求 |
| 多内核切换（Xray/sing-box/…） | 预留 `coreVariant`，首版只做 Xray | 控制范围 |

## 10. 未决问题

1. 内核最终选 **Xray-core（MPL-2.0）** 还是 **sing-box（GPL-3.0）**？→ 与许可决策绑定，见 `AGENT.md` 第 6 节。
2. 按应用分流（`trustedApplications`/`blockedApplications`）在目标 API 上的实际上限与统计口径。
3. geoip/geosite 是内置进 HAP 还是首次启动按需下载？→ 影响体积与首启体验。
4. 订阅更新与节点测速放在主进程还是扩展进程？→ 影响扩展进程职责与权限。
