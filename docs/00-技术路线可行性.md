## 0. 结论（先看这里）

### 必须把两件事分开讲，否则会做出错误决策

| 维度 | 判定 | 置信度 |
|---|---|---|
| **技术路线** | **可行（有条件）** | 中高 |
| **产品发行（中国大陆）** | **境内不可上架发行** | 中高（方向确定，细节需律师） |

**把这两条混在一起，会得出"技术不行"或"直接做就行"两种都错的结论。**

### 技术侧：可行

1. ✅ **系统提供了面向三方应用的正式 VPN API。** 本机 SDK 中 `@ohos.net.vpnExtension`（`@since 11`）
   提供"创建虚拟网卡 + 配置路由"，官方注释明确 **隧道协议由应用自己实现** —— 正是 v2rayN 的模型。
   三方 VPN **只需 `ohos.permission.INTERNET`**，**不需要 `MANAGE_VPN`**（该权限是 `system_basic`，普通应用拿不到也不需要）。
2. ✅📄 **门禁已查清**：三方应用的通行证**就是用户在授权弹窗点同意**（源码层校验的是授权落库记录 `vpnext_mode == "1"`），
   **不存在厂商白名单/审核作为硬门禁**；错误码 `2203001` 的真实含义是 **GUEST 访客账户被禁**，
   **不是**企业/白名单限制。
3. 🌐 **有真机先例**：至少 4 个公开项目走通该路线（x4h、Hey、Karing、etohos），其中两个记录了真机型号与系统版本。
4. ✅ **NDK 侧无障碍**：本机 clang 15.0.4 已实测可交叉编译出 `aarch64-linux-ohos` 的 `ELF64/AArch64` 目标文件；
   `ohpm 26.0.0.630` / `hvigorw 6.26.8` 实测可执行，依赖已成功拉取。

### 发行侧：境内不可上架

📄 这是**法律与平台政策双重封死**，不是"审核严一点"：

## 2. P1：系统能力 —— 证据

### 2.1 本地 SDK 中的 API（✅ 已验证）

文件：`...\ets\api\@ohos.net.vpnExtension.d.ts`，声明 `@syscap SystemCapability.Communication.NetManager.Vpn`，`@since 11`。

官方注释原文（关键）：
> "the VPN capabilities provided to third-party applications are primarily used for **creating virtual NICs and configuring VPN routing information**. The connection tunnel process and **internal connection protocols need to be implemented by the applications themselves**."

| API | since | 作用 |
|---|---|---|
| `startVpnExtensionAbility(want)` / `stopVpnExtensionAbility(want)` | 11 | 拉起/停止 VPN 扩展（触发用户授权） |
| `createVpnConnection(context)` | 11 | 创建连接对象 |
| `VpnConnection.create(config)` | 11 | 返回虚拟网卡 fd |
| `VpnConnection.protect(socketFd)` | 11 | 让 socket 绕过 VPN |
| `VpnConnection.protectProcessNet()` | 22 | 按进程绕过（**建议 `compatibleSdkVersion ≥ 22` 的核心理由**） |
| `VpnConnection.destroy()` / `destroy(vpnId)` | 11 / 20 | 销毁 |
| `createVpnObserver()` + `onAuthorizationResult()` | 26.0.0 | 授权结果回调 |

`VpnConfig`：`addresses`、`routes`、`dnsAddresses`、`searchDomains`、`mtu`(576–1500)、`isIPv4Accepted`、`isIPv6Accepted`、`isInternal`、`isBlocking`、`trustedApplications`、`blockedApplications`。

> ❓ `isInternal` / `isBlocking` **无权威语义定义**（官方只有一句话，无第二来源）。
> 两个参考实现都用默认值 false —— **建议沿用默认，不要凭猜测设置**。

### 2.2 权限模型与门禁（✅ 已验证 / 📄）

`PermissionDefinitions.json`：
```
ohos.permission.MANAGE_VPN      system_grant / system_basic / SYSTEM     since 10
ohos.permission.ENTERPRISE_VPN  system_grant / system_basic / MDM        since 26.0.0 / 仅 2in1
```

📄✅ **三方路径的门禁 = 用户授权落库**（OpenHarmony `networkvpn_service.cpp`）：
非系统调用方不查 `MANAGE_VPN`，而是查授权记录 `vpnext_mode == "1"` —— 即**用户在弹窗点同意**。
✅ `2203001` 的真实含义 = **GUEST 访客账户被拒**（错误码文档 + 源码 `if (accountType == GUEST)` 双重确认）。

声明方式（`entry/src/main/module.json5`）：
```json5
"requestPermissions": [{ "name": "ohos.permission.INTERNET" }],
"extensionAbilities": [{ "name": "VpnAbility", "srcEntry": "./ets/vpnability/VpnAbility.ets", "type": "vpn" }]
```

### 2.3 ⚠️ 生命周期：SDK 只声明 `onCreate` / `onDestroy`

✅ **实测**：本机 SDK 的 `@ohos.app.ability.VpnExtensionAbility.d.ts` **只有 `onCreate` / `onDestroy`**（均 `@since 11`）；
全 SDK 搜索**没有** `onConnect` / `onDisconnected`。

而参考实现 x4h **确实实现了** `onConnect`/`onDisconnected` —— 说明商业版运行时可能提供，但
**这不是公开 API 契约**，照抄有编译失败或行为不定的风险。

👉 **本项目的做法**：只在 `onCreate` 里自驱动（从 `want.parameters` 取配置、自行 async 启动），
`onDestroy` 收尾。**不要依赖未文档化的回调。**

> 另注：`onRequest` 同样不在 SDK 声明里，但先例 Hey 能用 → 说明该工程未开 `typeCheck`
> （`hvigor-config.json5` 默认 `false`）。**"能编译" ≠ "API 存在"**。

## 3. P2：数据面模型 —— 已改判（重要架构决策）

### 3.1 原方案（tun fd 直通）不可取

最初的设想（也是 x4h 的做法）是把 `VpnConnection.create()` 返回的 fd 直接交给 Xray 的 tun 入站。
**调研否定了这条路线**：

| 证据 | 内容 |
|---|---|
| 🌐 Hey（有真机日志） | **主动放弃**把 tun fd 交给核心：HarmonyOS 的 VPN fd **拒绝 `Fstat`** → gVisor `fdbased` 的 socket 判定失败；且现役 libXray 不再导出 `CGoSetTunFd` |
| 🌐 全部先例 | 可验证的数据面都是 `TUN → tun2socks → 本地 SOCKS → 核心出站` |
| ❓ x4h 的直通 | Star 1、README 168 字节、**无人验证**（`research/README.md` U3） |
| 环路问题 | 直通方案依赖 `protect(fd)`，但 Go 侧**没有任何 hook** 能把自建 socket 交给 ArkTS（`docs/design/core.md` §6.5）—— **原方案在此处无解** |

### 3.2 改为：本地 SOCKS/HTTP 入站 + tun2socks

```
TUN fd（VpnExtensionAbility 创建）
   └─ tun2socks（独立组件）→ 127.0.0.1:<socksPort>
        └─ Xray-core（本地 socks/http 入站）→ 按规则出站
```
- **环路解决**：把**自身包名放进 `VpnConfig.blockedApplications`**，应用自身 egress 不回到 TUN
  → **完全不需要 `protect()`**。这解决了原方案"无解"的那个问题。
- tun2socks 选型：`hev-socks5-tunnel`（纯 C，**不需要 Go fork，绕开 §4 的工具链问题**）或打过 `Fstat` 补丁的 gVisor tun2socks。

👉 该裁决已写入冻结契约 [`docs/design/ipc-contract.md`](design/ipc-contract.md) 第 2 节。

### 3.3 其他已查清的实战要点（🌐/📄）

| 要点 | 内容 |
|---|---|
| 网卡名 | **`vpn-tun` 是硬编码的固定接口名** → 可直接 `statistics.getIface[Tx\|Rx]Bytes('vpn-tun')` 做流量统计（最省事） |
| DNS | ⚠️ `dnsAddresses` **不是系统级 DNS**，官方限定"**被代理的应用**上网时"使用 → **存在 DNS 泄漏面** |
| 按应用分流 | ⚠️ 必须把**自身包名加入 `blockedApplications`** 防环路；二者互斥；⚠️ 鸿蒙**不向三方应用暴露已安装应用枚举** → 无法做 v2rayN 式"按进程选择"UI，只能让用户手输包名 |
| IPv6 | 🌐 要让 `::/0` 真正装到 TUN，需"空 gateway + `isDefaultRoute:false`"写法，否则 v6 **从物理网卡直出泄漏**；建议**始终接管 v6** |
| API 版本 | 当前 `compatibleSdkVersion 6.1.1(24)` **保守且安全，无需修改**；⚠️ 若降到 <22 会**失去 `want.parameters` 传参**；API 23 才把 routes 上限 1024→10000（v2rayN 等价物必然有大量路由规则） |

## 4. P3：Xray-core 在鸿蒙上编译 —— ❌ 当前受阻（已尸检到具体行）

### 4.1 Go 无 `GOOS=ohos`（🧪 已验证）

```
$ go version                        → go version go1.26.4 windows/amd64
$ go tool dist list | grep ohos     → （无输出）
```
✅ 主线 Go **没有**鸿蒙目标。社区 `GOOS=android GOARCH=arm64` 的借道方案是本项目唯一现成路径。

### 4.2 NDK 侧没问题（🧪 已验证）

```
$ clang --version                   → OHOS (dev) clang version 15.0.4
$ clang --target=aarch64-linux-ohos --sysroot=<NDK>/sysroot -D__MUSL__ -c probe.c
  → exit 0，产出 ELF64 / Machine: AArch64
```
✅ **NDK 侧彻底没问题**。问题全在 Go 侧。

### 4.3 借道 `GOOS=android` 实际失败——三个阻塞，逐个定位（🧪 实测）

| # | 阻塞 | 性质 | 状态 |
|---|---|---|---|
| (a) | **NDK 路径含空格**（`D:\Harmony\DevEco Studio\...`）→ Go 把 `CC` 截断成 `D:\Harmony\DevEco` | 环境 | 可用**无空格 junction（`mklink /J`）**绕过；8.3 短名在 D: 被禁用 |
| (b) | **OHOS sysroot 没有 `android/log.h`** → `runtime/cgo/gcc_android.c` 编译失败 | 环境 | 可用两行 no-op shim 头绕过 |
| (c) | **真正的阻塞**：Go 标准库 `net/cgo_resold.go:20` 类型不匹配 —— OHOS musl 把 `socklen_t` 声明为 `unsigned`，而 Go 的 android 端口假设 bionic 的宽度（传 `size_t`） | **工具链根本性** | **无编译开关可解**，需 patch Go 标准库或提供 bionic 兼容头 |

```
net/cgo_resold.go:20:76: cannot use _Ctype_size_t(len(b)) (value of type _Ctype_size_t)
  as _Ctype_socklen_t value in argument to (_C2func_getnameinfo)
```

✅ **关键判断**：这不是"Windows 上的 clang 不能编译鸿蒙"（见 4.2，能编译），
而是 **`GOOS=android` 的标准库假设与 OHOS 头文件冲突，与宿主平台无关**。
👉 参考实现 x4h 用的是**逐字节相同的配方**并发布了 32 MB 的 `libcore.so`，
但其仓库里没有这个 shim、也没有 `net` 替换 —— **说明它在仓库之外 patch 了 Go 工具链**（❓ 未证实）。

### 4.4 另一条更深的坑：cgo TLS 墙（🌐 社区，可信度中高）

即使编出来，`GOOS=android` 仍有运行期风险：Go 的 android 端口把 goroutine 指针 `g` 放在
**bionic 的固定 TLS 槽**，而 OHOS 跑 musl。**外来线程**（ArkTS / VPN 扩展进程）调 cgo 时，
槽为 0 可能碰巧能跑，槽是非零垃圾则被当作现成的 `g` → **SIGSEGV**。
物证：该产物缺少 `PT_TLS` 段；有真机崩溃栈（含机型与系统版本）。
**这是"能否稳定运行"的问题，不是"能否编译"的问题**，且是**概率性**的。

- 修法（❓ 未独立复现）：改用 `GOOS=openharmony` 的 **fork + TLSDESC**，产物须含 `PT_TLS` + `R_AARCH64_TLSDESC`，
  加 `CGO_CFLAGS="-ftls-model=global-dynamic"`，且**不能加 `-tags netgo`**。
- ⚠️ 供应链风险：官方 OpenHarmony SIG fork 停在 go1.24.5 且无上游合并证据；现役可用的是 **个人 fork**（星数很低）。
  → **为整个项目引入一个低星个人维护的 Go 工具链，是重大供应链风险**，必须由人决策。

### 4.5 由此得到的路线修正

**§3.2 的 SOCKS 模型在这里价值翻倍**：数据面改用纯 C 的 `hev-socks5-tunnel` 后，
TUN→SOCKS 那段**完全不需要 Go**，可以先用它把"系统能力"跑通；
Go 只负责"本地 SOCKS 入站 → 出站"，即使 Go 侧暂时不通，**产品的最小闭环也不至于全废**。
👉 这给了项目一条**降级但仍可用**的路径。

## 5. 内核选型：Xray-core vs sing-box

| | Xray-core | sing-box |
|---|---|---|
| 许可 | **MPL-2.0**（文件级 copyleft，**与 MIT 兼容**） | **GPL-3.0-or-later**（传染 + "不得暗示与原应用关联"附加条款） |
| 嵌入方式 | Go `-buildmode=c-shared` | `libbox`（gomobile 产物） |
| 鸿蒙先例 | 🌐 x4h | 🌐 Karing |
| 首版建议 | **选 Xray-core** | 备选，但一旦选用，许可策略必须整体重估 |

**许可决策的分量**：`x4h` / `Hey` / `etohos` / `Karing` **全部是 GPL 家族**，
本项目 `LICENSE` 是 MIT、`.gitmodules` 已确立"只参考不抄"的边界。
👉 **想保住 MIT，核心就只能从 MPL-2.0 的 Xray-core 起步** —— 这与参考边界是同一条纪律。

> ⚠️ 反面教材：Karing 只发预编译 HAP、不给源码，并在 README 里**自认 GPL 不合规**。不要重犯。

**可借鉴的合规工程实践（Hey）**：不内置任何服务器地址/订阅源/规则集/地区预设，

→ **内核 `.so` 缺失时应用仍能编译启动并给出明确错误**，工具链依赖从"DevEco + NDK + 仓颉"降到"DevEco + NDK"。

### 10.3 代码级缺陷 → 已按目标决策并修复

> 这两条不属于"文档写错"，而是**代码与冻结裁决不一致**。
> 决策标准只有一条：**它是否阻塞「像 v2rayN 一样绕过大陆」** —— 两条都阻塞，因此都修。
> 修复后**仍未在真机验证**（无真机），验证边界写在本节末。

「绕过大陆」的数据面链条是：
`设备流量 → TUN 网卡(fd) → tun2socks → 本地 127.0.0.1:SOCKS → 内核出站（按 geosite/geoip 分流）`。
下面两条分别打断这条链的**第 1 环**（网卡没被创建）与**第 2 环**（内核起不来）。

**(1) ✅ 已修复：生成的配置里带了一个 `tun` 入站，与冻结裁决冲突。**
`entry/src/main/golang/service/config/build.go` 的 `Build()` 曾生成
`inbounds[0] = {tag:"tun-in", protocol:"tun", settings:{name,MTU}}`；
而 `docs/design/ipc-contract.md` §2（**已冻结**）明确裁决"核心只负责本地 SOCKS/HTTP 入站，**不接管 tun**"。

**为什么必须修**：这条 tun 入站在内核侧会去读环境变量 `xray.tun.fd`，
`proxy/tun/tun_android.go:29` 的**默认值是 `"0"`**（不是报错），于是 fd 0（stdin）
会被 `unix.SetNonblock` 后当作 TUN 链路交给 gVisor。轻则日志全是指向错误的垃圾，
**重则 `instance.Start()` 直接失败 —— 本地 SOCKS 入站一起起不来，"绕过大陆"整个无从谈起。**

**落地改动**：
- 删除 tun 入站，以及只为它服务的常量（`TunName` / `DefaultMTU`）；
- **把 `sniffing` 从 tun 入站迁移到 `socks-in`**：tun2socks 交给 SOCKS 的多半是 IP，
  只有在入站侧嗅探 TLS SNI / HTTP Host 才能拿到域名，`geosite:cn` 这类按域名分流的规则
  才不会退化成只看 IP（`routeOnly: true` 的语义不变）；
- `config_test.go` 的断言**反转**：由"必须有 tun 入站"改为"**绝不能**有 tun 入站，且必须有 sniffing"。

**(2) ✅ 已修复：`VpnAbility.ets` 把网卡创建放在 `onConnect()` 里，而该方法不在 SDK 契约中。**
本机 SDK 的 `@ohos.app.ability.VpnExtensionAbility.d.ts`（`@since 11`）**只声明
`onCreate(want)` 与 `onDestroy()`**（✅ 本轮再次逐行复核确认），
**没有 `onConnect` / `onDisconnected`**。

**为什么必须修**：这不是"可能有问题"，而是**确定不会生效**。原代码把
`vpn.create(config)` 写在 `onConnect()` 里，而运行时不会回调一个契约中不存在的方法 →
**虚拟网卡永远不会被创建** → 流量根本不进 TUN → VPN 从第一步就不生效。

**落地改动**：
- 网卡创建移入 `onCreate` —— SDK 契约中唯一**保证**会被调用的入口；
- 新增幂等守卫（`vpnCreating` / `vpnCreated`）与 `ensureVpnCreated()` / `destroyVpn()`：
  `onConnect` / `onDisconnected` 保留为"若某版本确实回调则额外兜底"，与 `onCreate`
  共享守卫，**不会重复建网卡**（用幂等消除"是否会被回调"这个未知，无需先知道答案）；
- 顺带修正文件头那句"已按真实顺序搭好结构"的**过度声明**，明确标注哪两个方法在契约内。

**验证边界（诚实说明）**：
- Go 侧 🧪 `gofmt -l`（输出为空）、`go build ./...`、`go vet ./...`、
  `go test ./ipc/... ./service/... -count=1` **全绿**；其中
  `TestGeneratedConfigAcceptedByCoreLoader` 会用**内核自己的 loader** 验收生成配置，
  删除 tun 入站后仍通过，证明改动没有让配置失效。
- ArkTS 侧**未编译、未在真机验证**；`onCreate` 里创建网卡是否被系统正确回调，
  只能靠真机证明。

## 11. 数据面：tun2socks 插槽已落地（2026-10-11）

§10 修完的两处缺陷让"网卡会被创建""内核能起来"变成**可能** —— 但流量依然过不去，
因为缺的正是 §3.2 里那个独立组件。这一轮把它接上了。

### 11.1 选型：`hev-socks5-tunnel`（不是 Go / gVisor 版）

| 候选 | 结论 |
|---|---|
| **`heiher/hev-socks5-tunnel`**（纯 C） | ✅ **采用** |
| `xjasonlyu/tun2socks`（Go + gVisor，需 `Fstat` patch） | ❌ 需要 Go 工具链，正撞在 B2 上（Go 没有 `GOOS=ohos`） |

采用 hev 的两条硬理由：

1. **纯 C → 不需要 Go 工具链 fork**，数据面因此**完全绕开 B2**；
2. **MIT 许可** —— 这一条正好消除了本文件反复警告的风险：§9 第 3 条提醒过
   "为数据面引入 GPL 组件（例如某些 GPL 版 tun2socks）会让 MIT 边界失守"。
   hev 是 **MIT**，所以边界**没有**失守，仓库仍是 MIT + Xray-core(MPL-2.0)。

### 11.2 已落地的分层

| 层 | 文件 | 状态 |
|---|---|---|
| 加载/驱动（C++） | `cpp/tun2socks_bridge.{h,cpp}` —— `dlopen("libhevsocks5tun.so")`，把阻塞的 hev 主循环放进独立线程 | 🧪 语法检查通过 |
| NAPI 导出 | `cpp/napi_init.cpp` —— `Tun2socksStart/Stop/Stats/Available` | 🧪 同上 |
| 共享工具 | `cpp/native_util.h` —— `ownDirectory` / `escapeJsonString`（从 `napi_init.cpp` 提取） | 🧪 同上 |
| ArkTS 门面 | `ets/core/Bridge.ets` 的 `DataPlane`（`Bridge.ets` 的静态 `import` 首次启用） | ❓ 未编译 |
| 生命周期接线 | `ets/vpnability/VpnAbility.ets` —— 拿到 vfd 后 `startDataPlane(vfd)`；销毁网卡前先停数据面 | ❓ 未编译 |
| 构建 | `scripts/build-tun2socks.{ps1,sh}` → `entry/libs/arm64-v8a/libhevsocks5tun.so` | ❓ 配方从未跑过 |

设计与既有架构一致：hev 与 `libcore.so` 一样用 `dlopen` **惰性**加载，所以
**没有它也能构建、能启动**，失败时拿到的是带 `dlerror()` 文本的错误信封，而不是加载期崩溃。
`Tun2socks*` 四个符号全部返回与 Go 内核**同形**的信封，ArkTS 只有一条解析路径。

### 11.3 验证边界（诚实说明）

- 🧪 **C++ 做了真实交叉编译检查**：用本机 OHOS NDK 的 `clang++ 15.0.4`，参数
  `--target=aarch64-linux-ohos --sysroot=<ndk>/sysroot -D__MUSL__ -std=c++17 -Wall -Wextra -fsyntax-only`，
  `napi_init.cpp` 与 `tun2socks_bridge.cpp` **零告警通过**。
- ❓ **ArkTS 未编译**：本机没有 `hvigorw`，整个 HAP 从未构建过。
- ❓ **`.so` 未构建**：`scripts/build-tun2socks.*` 的配方是从上游 Makefile + 本机 NDK 布局
  推出来的，**从未执行成功**。三个已知风险点写在脚本头部（`build.mk` 是否随仓库提供、
  `third-part/lwip` 能否交叉到 OHOS musl、上游默认 `-Werror`）。
- ❓ **未在真机验证**。**U3 依然是 U3**：hev 的后端能否处理 OHOS 的 vNIC fd，没有新证据。

### 11.4 对 B2 的影响：范围缩小了一半

hev 让**数据面**不再依赖 Go 工具链，但**内核**（`libcore.so`）依然要 Go 交叉编译；
而 `scripts/build-core.ps1` 的头部记录了 Windows 宿主路径**当前是失败的** ——
Go 标准库的 `socklen_t` 与 OHOS musl 的 `typedef unsigned socklen_t` 宽度不一致，
必须打补丁而不是加参数；可用路线是 Linux / WSL。

也就是说：**B2 从"数据面与内核都卡"变成"只卡内核"**，而且卡点已被精确定位到一个
具体的类型不匹配，不再是"不知道行不行"。

### 11.5 下一步的顺序

1. **在 Linux / WSL 上把 `libcore.so` 编出来**（解掉 B2 的内核部分）——
   这是当前**最靠前**的工程任务：它在没有真机时就能推进，且结论可验证；
2. 在 Linux 上试编 `libhevsocks5tun.so`（`scripts/build-tun2socks.sh`），
   失败也**如实记录失败点**，不要绕过；
3. 采购真机（B3），然后按 `AGENT.md` §9 执行。
