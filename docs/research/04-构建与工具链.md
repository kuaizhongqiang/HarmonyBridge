### 13.6 签名与证书工作流

✅ `hap-sign-tool.jar` 在本机可用（已实测列出全部子命令）。

**标准签名链路**（工具支持的子命令本身即流程）：

```text
generate-keypair        # 生成密钥对（RSA/ECC），输出 JKS 或 P12 keystore
generate-csr            # 生成证书签名请求
generate-app-cert       # 生成应用证书（需 CA）
generate-profile-cert   # 生成 profile 签名证书
sign-profile            # 用 profile 签名证书签 provisioning profile（.p7b）
sign-app                # 用应用证书 + profile 签 HAP
verify-app / verify-profile   # 校验
```

**两种模式**：

| 模式 | 证书来源 | 用途 |
| --- | --- | --- |
| **调试（自动签名）** | DevEco Studio 通过华为账号自动申请调试证书 + 调试 profile | 真机调试；⚠️ 需登录华为开发者账号，且需将设备 UDID 加入 profile |
| **发布（手动签名）** | AGC 上申请的**发布证书**（.cer）+ **发布 profile**（.p7b）+ keystore/.p12 | 上架/正式分发 |

**本工程现状**：✅ `build-profile.json5` 的 `"signingConfigs": []` 为**空**，且 `products[0].signingConfig: "default"` 指向一个不存在的配置 → **当前工程无法直接产出已签名 HAP**。首次构建前必须在 DevEco 里配置签名（自动或手动）。

❓ **未证实/需确认**：
- 发布证书申请是否需要**企业开发者认证**（个人开发者能否申请发布证书）。审核指南 11.3 提到部分领域须法人实体提交，但证书申请本身的门槛**未找到权威说明**。
- 调试证书是否有**设备数量/有效期**限制（Android 侧有，HarmonyOS 侧未查到权威说明）。

### 13.8 `--target aarch64-linux-ohos` NDK 细节

✅ 从本机 NDK + 🌐 两个参考构建脚本归纳（[x4h build.sh](https://github.com/arror/x4h/blob/main/entry/src/main/golang/build.sh)、[log-adaptor arm64-v8a.sh](https://github.com/harmony-contrib/log-adaptor/blob/main/scripts/env/arm64-v8a.sh)）：

```bash
OHOS_NDK_HOME=<DevEco>/sdk/default/openharmony/native

CC=$OHOS_NDK_HOME/native/llvm/bin/clang              # ← 注意：x4h 里是 $OHOS_NDK_HOME/native/llvm/bin/clang
CFLAGS="-target aarch64-linux-ohos --sysroot=$OHOS_NDK_HOME/native/sysroot -D__MUSL__"
```

| 要点 | 说明 |
| --- | --- |
| target triple | `aarch64-linux-ohos`（**不是** `aarch64-linux-android`，也**不是** `aarch64-unknown-linux-ohos`） |
| sysroot | `$OHOS_NDK_HOME/native/sysroot` |
| **`-D__MUSL__`** | ⚠️ **必需**。OHOS 用 musl；不定义会让部分依赖走 glibc/bionic 分支 |
| `--sysroot=` 位置 | ✅ 本机 NDK 路径确实存在（已核） |
| 链接器 | 🌐 x4h 用 `-fuse-ld=lld`；🌐 Hey 用 `aarch64-unknown-linux-ohos-clang`（**另一种 triple 写法**，说明两种写法都可用，以实际 SDK 里存在的可执行文件为准） |
| **OHOS 专有库** | ✅ 本机 sysroot 含 `libohcommonevent.so`（x4h 链接 `-lohcommonevent`）、`libohaudio.so`、`libohcrypto.so` 等；🌐 x4h 另链接 `-lhilog_ndk.z -ltime_service_ndk` |
| `nativeapi_syscap_config.json` | ✅ 本机 `native/nativeapi_syscap_config.json` 存在（NDK 侧 SysCap 映射），但**grep `Vpn` 无命中** → NDK 侧无 VPN SysCap（与"VPN 是 ArkTS 侧能力"一致） |
| `syscap_tool.exe` | ✅ 本机 `toolchains/syscap_tool.exe` + `syscapcheck/sysCapSchema.json` 存在 |

## 14. API 级别要求

### 14.1 各能力的最低 API

| 能力 | 最低 API | 来源 |
| --- | --- | --- |
| **`VpnExtensionAbility` / `vpnExtension` 模块首批接口** | **API 11** | 📄 官方文档「本模块首批接口从 API version 11 开始支持」；✅ 本地 `@ohos.net.vpnExtension.d.ts` 全部 `@since 11` |
| `generateVpnId()` / `destroy(vpnId)` / `VpnConfig.vpnId`（多 VPN） | **20** | ✅ 本地 SDK `@since 20`；📄 且注明"系统多VPN能力仅支持 IPv4" |
| `protectProcessNet()` | **22** | ✅ 本地 SDK `@since 22` |
| `startVpnExtensionAbility` 支持 `want.parameters` 传参 | **22** | 📄 官方：`从API version 22开始，支持在VPN首次启动时传递want中的parameters字段` |
| `addresses` 上限 64→2000；`routes` 1024→10000；`trusted/blockedApplications` 64→256 | **API 23 起放宽** | ✅ 本地 SDK 注释 |
| `createVpnObserver()` / `VpnObserver.onAuthorizationResult()`（授权结果回调） | **26.0.0** | ✅ 本地 SDK `@since 26.0.0` |
| `MANAGE_VPN`（系统 VPN，非本路线） | — | ✅ `system_basic` / `SYSTEM`，三方不可用 |
| `ENTERPRISE_VPN`（MDM，非本路线） | **26.0.0** | ✅ 本地 `PermissionDefinitions.json`；`availableType: MDM`，`deviceTypes: ["2in1"]` |

### 14.2 对 `compatibleSdkVersion` 的建议

**关键洞察**：`modifier` 意义上的 API 依赖是分层的，**不需要为了用 API 11 的能力就把最低版本拉高**。要区分"**必须调用的 API**"与"**可选优化**"：

| 组件 | 是否需要高 API | 建议 |
| --- | --- | --- |
| `VpnExtensionAbility`（核心） | ❌ 只需 11 | 可兼容到 API 11 |
| `protectProcessNet()` | ⚠️ 需 22 | **强烈建议用**（一次保护整个进程，比逐 socket `protect()` 省事）→ 若用则 `compatibleSdkVersion ≥ 22` |
| `want.parameters` 传配置给扩展 | ⚠️ 需 22 | ⚠️ **重要**：x4h 与 Hey **都**用 `want.parameters` 把 VPN_CONFIG / 配置传给扩展。若最低版本 < 22，这条传参路径**不可用** |
| `generateVpnId()`（多 VPN） | 需 20 | 单 VPN 场景不需要 |
| `onAuthorizationResult` 回调 | 需 26 | 拿授权结果靠回调；🔄 但 26 以下可用 `startVpnExtensionAbility` 的 success/error 间接判断（🌐 Hey 就是这么做的：await 通过即提示"VPN已授权"） |
| 参考先例的最低版本 | — | 🌐 Hey `compatibleSdkVersion = 6.0.1(21)`；🌐 Karing `compatibleSdkVersion 6.1.0(23)` / `targetSdkVersion 6.1.1(24)` |

**结论建议**：

| 选择 | 理由 |
| --- | --- |
| ⭐ **`compatibleSdkVersion = "6.1.0(23)"`（API 23）** | ① 高于 22 → `want.parameters` 与 `protectProcessNet()` 都可用；② 拿到 API 23 的限额放宽（routes 10000 / addresses 2000 / app 列表 256）——**对代理客户端的分流规则数量很关键**（v2rayN 等价物必然有大量路由规则）；③ 与 Karing 的最低版本一致，说明是可行的下限；④ ⚠️ 若要支持 API 21/22 的老设备，只能牺牲限额与传参便利 |
| `compatibleSdkVersion = "6.0.1(21)"`（API 21） | 覆盖更老设备，但 **`want.parameters` 不可用**（<22）→ 需改用其他传参方式（如共享偏好/文件）；🌐 Hey 就是 21，说明可行，代价是配置传递更绕 |
| ⚠️ 不要盲目拉到 26 | 当前工程 `targetSdkVersion = "26.0.0"` 是**目标**版本，不是最低兼容；拉高 `compatibleSdkVersion` 会白白丢掉设备覆盖 |

**当前工程现状评估**：✅ `compatibleSdkVersion = "6.1.1(24)"` → **是保守且安全的选择**（24 > 23，所有需要的 API 都可用）。**无需修改**；若想放宽设备覆盖，可考虑降到 `6.1.0(23)`（Karing 的选择）。

### 14.3 与本机 SDK 的匹配性

| 项 | 值 | 匹配 |
| --- | --- | --- |
| 工程 `compatibleSdkVersion` | API 24 | ✅ ≤ SDK 的 26 |
| 工程 `targetSdkVersion` | 26.0.0 | ✅ = SDK 的 26 |
| SDK apiVersion | 26 | ✅ |

→ ✅ **版本层面无冲突，本机可直接编译本工程。**
