# 02 · 核心移植方案

> 回答 Lead 问题 7–11。核心结论：**主线 Go 至今不支持 HarmonyOS**；`GOOS=android` 能编出可加载的 `.so`，但在外来线程调 cgo 时会 SIGSEGV，**必须改用 `GOOS=openharmony` 的第三方 Go fork + TLSDESC**；数据面**推荐 tun2socks**（有真机跑通记录），不建议直接使用核心自带 tun inbound。

## 8. `GOOS=android` 手法评估

### 8.1 它长什么样（✅ 两个独立项目一致）

```bash
export CC=$OHOS_NDK_HOME/native/llvm/bin/clang
export CFLAGS="-target aarch64-linux-ohos --sysroot=${OHOS_NDK_HOME}/native/sysroot -D__MUSL__"
export CGO_ENABLED=1
export GOOS=android            # ← 关键：假装是 Android
export GOARCH=arm64
export CGO_CFLAGS="-g -O2 `$LLVMCONFIG --cflags` --target=aarch64-linux-ohos --sysroot=$OHOS_NDK_HOME/native/sysroot"
export CGO_LDFLAGS="--target=aarch64-linux-ohos -fuse-ld=lld -lohcommonevent -lhilog_ndk.z -ltime_service_ndk"
go build -ldflags "-s -w" -buildmode=c-shared -o libcore.so .
```

- 🌐 [arror/x4h `entry/src/main/golang/build.sh`](https://github.com/arror/x4h/blob/main/entry/src/main/golang/build.sh)（显式带 `-D__MUSL__`）
- 🌐 [harmony-contrib/log-adaptor `scripts/env/arm64-v8a.sh`](https://github.com/harmony-contrib/log-adaptor/blob/main/scripts/env/arm64-v8a.sh)（同样的配方，同样 `GOOS=android`）

### 8.2 为什么"看起来"能用

`GOOS=android` 让 Go 的 `cmd/link`/runtime 走 linux-arm64 分支，接受 `--target=aarch64-linux-ohos` 的 clang 产物，于是：
- 能产出 ELF shared object，`dlopen` 成功；
- Go 侧主动调用 libc（`getrandom`、`epoll`、`clone`）走 linux 系统调用路径，OHOS 内核接口兼容；
- cgo 符号能被导出、能被 N-API 调到（🌐 Hey 崩溃栈证明 `libheyvpn.so` 确实调到了 Go 的 C 导出符号）。

**核心 trick 是 `-D__MUSL__`**：OHOS 用 musl，而 Go 的 `android` target 假设 bionic。`-D__MUSL__` 用来让部分 C 侧代码（如 gVisor / 第三方依赖）走 musl 分支。但**它无法修复 Go runtime 自身的 TLS 假设**（下面 §8.3）。

### 8.3 真正的致命缺陷：TLS 模型

> 🌐 这是本次调研**最有价值的单条发现**，来自 Hey 一手排查记录
> [docs/harmonyos-go-tls-wall.md](https://github.com/popsiclelmlm/Hey/blob/main/docs/harmonyos-go-tls-wall.md)（可信度中：含崩溃栈、真机型号、可复核的 readelf 结论；**但我方未独立复现**）

**机制**：Android/bionic 把 Go 的 goroutine 指针 `g` 放在**固定 TLS 槽**里。HarmonyOS 跑 musl，那个固定槽**不归 Go runtime 管**：

| 场景 | `GOOS=android` 的结果 |
| --- | --- |
| Go 自己创建线程 | ✅ 正常（Go 自己初始化了槽） |
| **外来线程**（ArkTS、VPN 扩展进程）调 cgo | ❌ 槽里恰好是 0 → Go 走 `needm` 补状态，**碰巧能跑**；槽里是非零垃圾 → Go 当它是现成的 `g` 直接用 → **SIGSEGV** |

**关键观测**：`llvm-readelf -l libxray.so | grep TLS` **为空** —— 也就是产物里**没有真正的 ELF `PT_TLS` 段**。这就是"bionic 固定槽"假设的物证。

**真实崩溃现场**（🌐 真机 ALN-AL80 / HarmonyOS 6.1.0.117 / API 23）：

```text
Reason: Signal:SIGSEGV(SEGV_MAPERR)@0x000103ffd50323b7
Process name: com.lmlm.hey:vpn   life time: 2s
#00 pc 0x...fc3e38 libxray.so
#02 pc 0x...0106e4 libheyvpn.so
#03 libace_napi.z.so ArkNativeFunctionCallBack
#06 at setNativeTunFd (HeyNative.ets:111)
#07 at startVpn (HeyVpnAbility.ets:101)
```

**最折磨人的性质**：这个 bug 是**概率性/环境相关**的——槽里是 0 还是垃圾取决于线程布局、TLS 初值、加载顺序。所以会出现"**以前能跑，现在崩**"（同一台设备连旧版二进制都崩了），也会出现"**只在某条路径崩**"（x4h 的写法可能刚好没踩到，Hey 的 `CGoSetTunFd` 踩到了）。**这不是"能否编译"的问题，而是"能否稳定运行"的问题。**

### 8.4 修复：改用 `GOOS=openharmony` + TLSDESC

🌐 [Hey `building-native-cores.md`](https://github.com/popsiclelmlm/Hey/blob/main/docs/building-native-cores.md) 给出三种编法的对比（可信度中）：

| 编法 | `g` 存哪 | 在 HarmonyOS (musl) 上的结果 |
| --- | --- | --- |
| 标准 Go + `GOOS=android` | bionic 固定 TLS 槽 | `dlopen` 能过，但**外来线程那个槽是垃圾 → cgo→Go SIGSEGV** |
| 标准 Go + `GOOS=linux` | initial-exec TLS | musl **拒绝 `dlopen`** 含 IE-TLS 的库 → **整个原生桥加载失败** |
| **OHOS fork + `GOOS=openharmony`** | **TLSDESC（通用动态 TLS）** | `dlopen` 能过 **且** 外来线程 cgo 正常 ✅ |

**产物校验（必须做，作为构建门禁）**：

```bash
strings -a libxray.so | grep -m1 'GOOS=openharmony'
strings -a libxray.so | grep -m1 -o 'go1\.26\.[0-9]*'
llvm-readelf -l libxray.so | grep -i TLS        # 必须出现 PT_TLS
llvm-readelf -r libxray.so | grep -i TLSDESC    # 必须出现 R_AARCH64_TLSDESC
llvm-nm -D libxray.so | grep ' T .*CGo'         # 导出集核对
```

**同源约束**（必须遵守，否则照样崩）：
- `CGO_CFLAGS="-ftls-model=global-dynamic"`（去掉其余 initial-exec TLS 重定位）
- **不能加 `-tags netgo`**：openharmony 的 net port 需要 cgo，加了会报 `_C_getifaddrs undefined`
- 需要向 Go 传的环境变量（如 `XRAY_LOCATION_ASSET`）**必须在首次 `dlopen` 之前 `setenv`**
  > 🌐 原因（Hey §5，可信度中，但机制解释很硬）：① Go 只在运行时初始化时**拷贝一次** `environ`，之后 `setenv` 它看不到；② c-shared 运行时在 `dlopen` 返回后**另起线程异步初始化**，此时 C 侧 `setenv` 会让 musl realloc/free 旧数组，Go 初始化线程读到野指针 → **SIGSEGV**。Hey 记录这条正是"迁到 libXray v26.7.28 后 VPN 扩展进程启动就崩"的真因。

### 8.5 其他已知失败模式

| 失败模式 | 表现 | 处理 |
| --- | --- | --- |
| **gVisor `Fstat` 拒绝** | HarmonyOS VPN fd 支持 `readv`/`writev`，但**拒绝 `Fstat`**。gVisor `fdbased` endpoint 默认用 `unix.Fstat` 判断 fd 是否 socket → 失败 → tun2socks `engine.Start()` **`log.Fatal` 退出整个进程** | 必须 patch：`func isSocketFD(fd int) (bool, error) { return false, nil }`。对 tun2socks 是 **required**；对纯 SOCKS 版 libxray 是尽力而为 |
| 官方 SIG fork 不支持 `-buildmode=c-shared` | 标题级证据（未证实正文） | 用第三方 fork，或改成"主程序 + 静态链接" |
| Go 版本鸿沟 | 老 fork (go1.24.5) 编不动 go1.25+/1.26 的新核 | 用 star4277/ohos-go v1.26.5-beta1 |
| 工具链被误删 | `<repo>/build/` 会被 `hvigor clean` 删掉 | 工具链放仓库外（如 `~/hey-ohos-build/`） |

### 8.6 可复现性与跨版本稳定性评估

| 维度 | 评估 |
| --- | --- |
| 编译可复现 | **中高**。构建脚本是纯 shell + 环境变量，x4h 与 log-adaptor 两个独立仓库配方一致；能 pin 版本即可复现 |
| 运行稳定性 | **中**（`GOOS=android`）/ **中高**（`GOOS=openharmony` + TLSDESC）。前者有概率性 SIGSEGV，后者被两个项目在真机上验证，但样本量小 |
| 跨 Xray-core 版本稳定性 | **低-中**。Hey §6 记录了明确案例：`CGoSetTunFd`（2026-04-01 加入）、`xray-core v1.250803.0` 无 `proxy/tun`/`TunFdKey`、`v1.260206.0` 有但 go.mod 要求 go1.25.7 → **Go 版本与核心特性互相锁死**。升级核心 = 升级工具链 = 重做真机验证 |
| 工具链可持续性 | **低**。依赖 4-star 个人 fork；官方 SIG fork 已停在 go1.24.5 且无上游合并证据 |

**结论**：`GOOS=android` 这条 trick **技术上确实"能用"**（x4h 就是这么发的），但它建立在**未文档化的 TLS 假设**上，属于"能跑但不可靠"。**不建议作为长期主线**。若采用，必须建立 §8.4 的产物门禁 + 真机回归。

| 路线 | 评估 |
| --- | --- |
| **C**（如 hev-socks5-tunnel） | ✅ **完全可行且已被验证**。🌐 Hey 把 [heiher/hev-socks5-tunnel](https://github.com/heiher/hev-socks5-tunnel) 2.9.0（含 `hev-task-system`/`yaml` 子模块）**纯 C 交叉编译**：`aarch64-unknown-linux-ohos-clang` + sysroot + `--target=aarch64-linux-ohos`，**不需要 Go fork**，绕开整个 TLS 墙。产物 `libhevsocks5tun.so` 导出 3 个符号，作为**可选的高性能 tun2socks 引擎**。这是**低风险的第三条路**。 |
| **Rust** | ✅ 生态上 Rust 对 OHOS 支持良好（`target aarch64-linux-ohos` 是 Rust 官方 tier-2/3 target，与 Go 形成鲜明对比）。🌐 **etohos 就是证据**：把 **EasyTier（Rust mesh VPN）** 编进 OHOS，ArkTS 通过 NAPI `setTunFd(running_inst, fd)` 把 tun fd 交给 Rust 侧。⚠️ 但需注意：etohos 是 **Flutter + Rust** 混合工程（Dart 为主），其 `VpnExtAbility.ets` **是空实现**，真正的 VPN 逻辑放在 `EntryAbility.ets`（主进程），且**主进程直接 `create()` 拿 fd 交给 Rust**——与 §5.4「扩展进程独立」的模型不同，需自行判断其取舍。 |
| **C++** | ✅ 可行（🌐 Hey 的主体原生桥 `libheyvpn.so` 就是 C++ N-API + CMake，通过 `externalNativeOptions` 参与 hvigor 构建）。但**重写一个代理核心（VLESS/VMess/Trojan/Reality/uTLS）的成本极高**，不值得。 |

**评估**：**"Rust/C 写数据面 + Go 写协议核心"这一混合方案值得考虑** —— 用 Go（Xray）做协议出站，用 C（hev）或 Rust 做 tun2socks，完全避开 Go 在 tun fd 上的所有坑（§8.5 Fstat patch、`CGoSetTunFd`）。这正是 Hey 的现役架构。

### (b) `childProcessManager` + `@ohos.app.ability.ChildProcess`

✅ **本机 SDK 确认存在**（上一轮已核实）：

| API | `@since` | 语义 |
| --- | --- | --- |
| `startChildProcess(srcEntry, startMode): Promise<number>` | 11 | `StartMode` 枚举。⚠️ 文档注释：`ChildProcess.onStart` 执行完，**子进程自动销毁** |
| `startArkChildProcess(srcEntry, args, options?): Promise<number>` | 12 | 同上，注释：函数执行完**不会**自动销毁，需显式销毁 |
| `startNativeChildProcess(entryPoint, args, options?): Promise<number>` | 13 | 加载 **动态库**并调用其中的入口函数 |
| `isArkChildProcessSupported(): boolean` | 26.0.0 | 某些设备不支持创建 ark 子进程，建议先探测 |
| `isNativeChildProcessSupported(): boolean` | 26.0.0 | 同上（native 子进程） |

相关文件：`@ohos.app.ability.ChildProcess.d.ts`、`ChildProcessArgs.d.ts`、`ChildProcessOptions.d.ts`、`childProcessManager.d.ts`。

**能否继承 tun fd？**
> ❓ **未证实，且有较强的反向理由。** `childProcessManager` 是**spawn 语义**（按 `srcEntry` 路径启动新进程），**不是 `fork()`**。spawn 出的新进程拥有**独立的 fd 表**，父进程的 tun fd 编号在其中无意义。SDK 亦无任何 fd 传递 API（`ChildProcessArgs` 是参数容器，未见 fd 语义）。**要跨进程传 fd 只能走 `sendmsg`+`SCM_RIGHTS`（unix domain socket）或 `binder` 的 fd 传递能力，SDK 未暴露。**
>
> 所以 (b) **不能**用来"让子进程持有 tun fd"。但它**可以**用来：
> - 把**协议核心**放子进程（核心只需 TCP/UDP 出站，不碰 tun）→ ✅ 可行；
> - 与 (c) 组合：**主/扩展进程持有 tun fd 跑 tun2socks**，子进程跑纯 SOCKS 出口核心。
>
> ⚠️ 若如此拆分，`protectProcessNet()` 的保护范围是否覆盖子进程**未证实**，需实测；否则子进程的核心出站会被自己抓回 tun 形成环路。

### (c) tun2socks + SOCKS/HTTP 代理核心 ⭐

**这是本次调研最推荐的路线**，理由：

1. ✅ **已有真机跑通记录**：🌐 Hey 的现役数据面就是它，真机 ALN-AL80 / HarmonyOS 6.1 上「原来的'VPN 扩展没有回写启动完成状态'已消失，VPN 能连上，也能走通流量」。
2. ✅ **核心与数据面解耦**：核心只提供本地 SOCKS 入站（不需要 `proxy/tun`、`TunFdKey`、`CGoSetTunFd`），因此**不受 Go 版本鸿沟约束**，可以自由 pin 核心版本。
3. ✅ **两种 tun2socks 实现可选**：gVisor（`xjasonlyu/tun2socks` v2.6.0，Go）或 hev-socks5-tunnel（纯 C，性能更好）。前者需 Fstat patch，后者不需要（不碰 Go）。
4. ✅ 架构与桌面 v2rayN 的 tun2socks 模式**同构**，本工程已有的 v2rayN 参考知识可复用。

**代价（必须承认）**：多一层用户态转发（读 tun → 用户态 TCP/IP 栈 → 本地 SOCKS → 核心再封装），性能与内存都不如 native-TUN 干净，高吞吐场景下是瓶颈。

**推荐组合**：
```text
HarmonyOS VPN TUN fd
  → libheytun2socks.so (gVisor，需 Fstat patch)  或  libhevsocks5tun.so (纯 C，无 patch)
  → 127.0.0.1:<port> (本地 SOCKS/mixed 入站)
  → Xray-core (MPL-2.0) outbound
```

### (d) 纯 ArkTS 用户态 TCP/IP 栈

**❌ 不可行。** 理由（含定量说明）：

| 为什么不行 | 说明 |
| --- | --- |
| **性能数量级差距** | 用户态网络栈要在**每个数据包**上做 IP 头解析、TCP 状态机、校验和、重传/拥塞控制、缓冲区管理。ArkTS 运行在 ArkCompiler（方舟）上，是**托管、带 GC** 的运行时；即使有 JIT/AOT，逐包处理也不可能达到 Go（gVisor netstack，已是该场景的性能下限）或者 C（hev，用 `hev-task-system` 协程 + epoll）的水平。 |
| **无 0 拷贝 / 无零依赖原语** | tun fd 的 `readv`/`writev` 在 ArkTS 侧只能通过 NAPI 转手；ArkTS 没有可用的 `mmap` 环形缓冲区、没有可控的 `epoll` 循环、无法避免跨语言拷贝。 |
| **GC 停顿** | 高包速率下会产生巨量短命对象（sk_buff 等价物），GC 停顿直接表现为丢包与抖动。 |
| **施工量** | 需要自己实现 TCP（含 SACK/窗口缩放）、UDP、ICMP、DNS 代理、分片重组。这是"重写 lwIP"，以项目规模不现实。 |
| **反面证据** | 🌐 所有已成功的 OHOS 代理实现（x4h / Hey / Karing / etohos）**无一**走纯 ArkTS 数据面——全部下沉到 native（Go/C/Rust）。 |

**结论**：ArkTS 只应做**配置生成、UI、生命周期编排**。数据面必须下沉 native。

❓ 未在本次调研中发现 v2rayN 的 HarmonyOS 分支/PR/issue 相关材料。**（未深入，与本路线无关。）**

| 鸿蒙 Clash / ClashMeta / NekoBox / Hiddify / v2rayN OHOS | ❓ **未找到**已发布的 OHOS 原生实现。搜索命中的多为 Android 版或"如何在鸿蒙上装 v2ray"的教程（如 [garygeng.net](https://www.garygeng.net/software/huaweihongmengnextshoujizenmeanzhuangv2ray/)，🌐低，且内容疑似通过 Android 兼容层侧载） |
| Huawei 官方 `@ohos.net.vpnExtension` 之外的 VPN 能力 | `ENTERPRISE_VPN`（MDM，`2in1` only）、IPsec/L2TP/OpenVPN 系统 VPN 走 `SUPPORT_SYSVPN` 分支（需 `MANAGE_VPN` / 系统签名）→ **对三方应用不可用** |

### 11.6 prior-art 汇总结论

1. **路线在真机上被证明可行**（Hey + Karing + x4h + etohos 四个独立实现，都能创建 VPN 并跑流量）。**这是"技术可行"的最强证据。**
2. **生态整体非常年轻且不成熟**：最大的项目 72 stars；除 Hey 外**几乎没有技术文档**；x4h 甚至不写 README；Karing 闭源发 GPL 二进制；etohos 架构反模式。
3. **发行方式无一例外是"侧载"**（源码 / GitHub Release HAP），**没有一个上了 AppGallery** —— 与 [03 文档](03-合规与上架风险.md) 的合规结论完全一致。
4. **GPL 传染是普遍现象**：x4h(GPL-3.0)、Hey(GPL-3.0)、etohos(LGPL-3.0)、Karing(sing-box GPL-3.0) —— **只有 Xray-core 本身是 MPL-2.0**。本项目若想保持宽松许可，必须**只参考、不抄代码**，并从 MPL-2.0 的 Xray-core 起步。
5. **没有找到"直接用核心自带 tun inbound"的成功案例** —— 除 x4h 外，所有成熟实现都走 tun2socks。
