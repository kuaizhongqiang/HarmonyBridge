```powershell

cd Bridge
git lfs install                # 🧪 每台机器一次
```

`bootstrap.ps1` 会做：`git lfs install` → 拉取 `third_party/v2rayN`（shallow）→ 调 `check-env.ps1`。

## 3. 工程配置

### 3.1 API 基线

`build-profile.json5`（工程根）：

```json5
"targetSdkVersion": "26.0.0",
"compatibleSdkVersion": "6.1.1(24)",
"runtimeOS": "HarmonyOS",
"buildOption": { "nativeCompiler": "BiSheng" }
```

- `compatibleSdkVersion` 决定**能用到哪些 API**。本项目依赖 `@ohos.net.vpnExtension`（`@since 11`），
  以及可选的 `protectProcessNet()`（22）、`generateVpnId()`（20）、`onAuthorizationResult()`（26）。
  **API 24 基线足以覆盖 VPN 主链路**；用到 26 的特性需再做条件判断。
- `nativeCompiler: BiSheng`（毕昇编译器）是模板默认，保持不动。

### 3.2 `local.properties`

该文件由 DevEco Studio 生成且**不入库**。内容应指向本机 SDK：

```properties
sdk.dir=D\:\\Harmony\\DevEco Studio\\sdk
```

> ⚠️ 本机当前该文件几乎是空的 —— 用 DevEco Studio 打开工程并 sync 一次，它会被自动补全。
> 如果 sync 报找不到 SDK，就手动补上面这行。

### 3.3 依赖

- 工程级 `oh-package.json5`：`devDependencies` 只有 `@ohos/hypium`、`@ohos/hamock`（测试框架），**无运行时依赖**。
- 模块级 `entry/oh-package.json5`：注册本地 NAPI 类型包 `libbridge.so`。
- **本项目刻意不引入第三方 ohpm 包**（参考实现用了 `@pura/harmony-utils`，我们不跟），
  目的是把依赖风险和供应链面压到零。

安装依赖：

```powershell
& "D:\Harmony\DevEco Studio\tools\ohpm\bin\ohpm.bat" install
```

## 4. 签名与证书

**签名材料一律不入库**（`.gitignore` 已拦截 `*.p12` / `*.cer` / `*.p7b` / `*.keystore` / `*.jks` / `/signature/`）。

> 🔴 **实测结论（2026-10-12，重要）**：**SDK 自带的 OpenHarmony 演示证书在华为真机上装不上去。**
> 我们按 OpenHarmony 手工签名流程真做了一遍（生成含本机 UDID 的 debug profile →
> `hap-sign-tool sign-profile` → `sign-app`，**签名本身两步都 `success`**），
> 但真机拒绝 profile 的 pkcs7 信任链：
> `code:9568257 error: fail to verify pkcs7 file.`（`OpenHarmonyProfileDebug.pem` 与
> `Release.pem` 两种变体都试过）
> 👉 **必须用 DevEco「自动签名」（AGC 签发）**，见下方"签名的正路"。
> 另一个坑：`keytool -exportcert -alias "openharmony application release"` 导出的是
> **自签版本**，拿它当叶证书做链校验必然失败（`11013002 Signature does not match`）；
> 可用的叶证书在 `UnsgnedDebugProfileTemplate.json` 的 `bundle-info.development-certificate` 里。
>
> 顺带记录两个前置报错，便于快速归因：
> `9568320 no signature file`（HAP 根本没签名）→ 卡在构建阶段，看产物名有没有 `unsigned`。

SDK 自带的调试用材料（**仅供参考和本地调试，不可用于华为真机**）：

```
D:\Harmony\DevEco Studio\sdk\default\openharmony\toolchains\lib\
├── hap-sign-tool.jar                 ← 签名工具
├── OpenHarmony.p12                   ← 调试用密钥库
├── OpenHarmonyProfileDebug.pem       ← 调试用 Profile 证书
├── OpenHarmonyProfileRelease.pem     ← 发布用 Profile 证书
├── UnsgnedDebugProfileTemplate.json  ← 未签名调试 Profile 模板
└── UnsgnedReleasedProfileTemplate.json
```

签名的正路（🧪 已在真机跑通）：**在 DevEco Studio 里配置自动签名**
（`File → Project Structure → Signing Configs` → 勾选 `Automatically generate signature`；
需登录**已实名认证**的华为开发者账号；**且手机必须先通过 USB 连上**
—— IDE 要把设备 UDID 注册进调试 Profile）。

成功判据有**两条，都变才算成功**（UI 提示成功但没变 = 静默失败）：

1. `build-profile.json5` 的 `app.signingConfigs` 从 `[]` 变为含
   `material{storeFile, certpath, profile, keyAlias, …}`；
2. `C:\Users\<你>\.ohos\config\` 出现 `*.p12` / `*.cer` / `*.p7b`。

> 🔴 **这两处都含凭据与本机绝对路径 → 提交前必须排除 `build-profile.json5`。**
> 见 [`AGENT.md`](../AGENT.md) 第 9 节。

手工签名流程（**仅供理解原理；华为真机会拒绝 SDK 演示证书，见上**）：

```
hap-sign-tool.jar sign-app
  -keyAlias ... -keyPwd ... -keystore ... -keystorePwd ...
  -appCertFile ... -profileFile ... -inFile unsigned.hap -outFile signed.hap
  -signAlg SHA256withECDSA -mode localSign -profileSigned 1
```

> ❓ 发布签名需要**华为开发者账号 + 应用证书 + Profile**（Profile 里绑定 bundleName 与证书指纹）。
> 这一步没有账号无法完成，属于外部依赖。

## 5. 构建

### 5.1 用 DevEco Studio（推荐）

打开工程 → sync → `Build → Build Hap(s)`。IDE 会处理 ohpm 安装、CMake/NAPI 编译、签名。

### 5.2 用命令行 ✅ 已实测通过

工程根**没有** `hvigorw` 包装脚本，因此用 DevEco 内置的。
**必须**设 `DEVECO_SDK_HOME` 与 `JAVA_HOME`，否则会分别报
`Invalid value of 'DEVECO_SDK_HOME'` 和 `spawn java ENOENT`：

```powershell
$dev  = "D:\Harmony\DevEco Studio"
$env:DEVECO_SDK_HOME = "$dev\sdk"          # 不设 → 00303217 Configuration Error
$env:JAVA_HOME       = "$dev\jbr"          # 不设 → 00308018 spawn java ENOENT
$env:PATH            = "$dev\jbr\bin;$env:PATH"

& "$dev\tools\ohpm\bin\ohpm.bat" install
& "$dev\tools\hvigor\bin\hvigorw.bat" --mode module -p product=default -p buildMode=debug assembleHap --no-daemon
```

**实测结果（2026-10-11，本机）**：

```
> hvigor Finished :entry:default@CompileArkTS...            ← 44 个 .ets 全部编译通过
> hvigor Finished :entry:default@BuildNativeWithCmake...
> hvigor Finished :entry:default@BuildNativeWithNinja...    ← NAPI C++ 桥编译通过
> hvigor Finished :entry:default@PackageHap... after 386 ms
> hvigor WARN: Will skip sign 'hos_hap'. No signingConfigs profile is configured
> hvigor BUILD SUCCESSFUL in 2 s 694 ms
```

> 🧪 **第二轮（2026-10-11，`clean` 后全量重编）**：`33 tasks in total: 32 executed, 1 up-to-date`，
> `CompileArkTS` 真正执行了 4.6 s（不是 `UP-TO-DATE`），`BUILD SUCCESSFUL in 10 s 425 ms`，
> 产物 `entry-default-unsigned.hap` **2.4 MB**（未签名）。
>
> ⚠️ **只报 `UP-TO-DATE` 的那次构建不能当作 ArkTS 侧的验证** —— 它可能吃的是上一次的增量缓存。
> 要断言"ArkTS 编译通过"，必须先 `hvigorw clean` 再编。
>
> 本轮构建的告警（不影响 `BUILD SUCCESSFUL`，且**均非本轮改动引入**）：
> `app_name` 在 `AppScope` 与 `entry` 重复声明；`utils/Clipboard.ets:21` 未声明
> `ohos.permission.READ_PASTEBOARD`；`components/ConnectionStatusBadge.ets:46` 用了 `fill`
> （`@since 26.0.0`）而 `compatibleSdkVersion` 是 24；`pages/Index.ets:71` `getContext` 已废弃；
> `cpp/napi_init.cpp:118` 用了 C++17 的 if-init 写法（`-Wc++17-extensions`）。

产物（**均不入库**）：

| 产物 | 大小 | 说明 |
|---|---|---|
| `entry/build/default/outputs/default/entry-default-unsigned.hap` | 2.1 MB → **2.4 MB** | **未签名** HAP（第二列为第二轮 `clean` 重编后的大小） |
| HAP 内 `ets/modules.abc` | 492 KB → 随代码增长 | ArkTS 编译产物 |
| HAP 内 `libs/arm64-v8a/libbridge.so` | 107 KB（剥离后） | NAPI 桥，**确认已打进包** |
| `entry/build/.../libbridge.so` | 468 KB（未剥离） | arm64-v8a |

> ✅ 这一步证明了：**ArkTS 侧与 NAPI 原生桥都能真实编译并打包**，不需要真机。
> 唯一缺的是签名 —— `signingConfigs` 为空，所以产出的是 `-unsigned.hap`。

> ⚠️ **读构建日志的坑**：不要用 PowerShell 管道抓 hvigor 输出，它会把行按终端宽度截断、丢掉
> `文件:行:列`。要重定向到文件再读，并先剥掉 ANSI 转义：
> ```powershell
> cmd /c "`"$dev\tools\hvigor\bin\hvigorw.bat`" ... > `"$env:TEMP\build.log`" 2>&1"
> ((Get-Content "$env:TEMP\build.log" -Raw) -replace "\x1b\[[0-9;]*m", '') -split "`r?`n" | Select-String 'Error Message:'
> ```
> 另注：编译**干净**时日志里**不会**出现 `COMPILE RESULT:SUCCESS`，只有
> `Finished :entry:default@CompileArkTS`；出现 `COMPILE RESULT:FAIL {ERROR:n}` 才是有诊断。

### 5.3 原生内核（Go → `libcore.so`）

这是与 hvigor 分离的**独立构建**：

```powershell
.\scripts\build-core.ps1          # Windows
# 或（Linux/macOS/Git-Bash）
bash scripts/build-core.sh
```

脚本会定位 OHOS NDK，设置 `GOOS=android GOARCH=arm64 CGO_ENABLED=1` 与
`--target=aarch64-linux-ohos --sysroot=<NDK>/native/sysroot`，用 `-buildmode=c-shared`
产出 `libcore.so` 并放到 `entry/libs/arm64-v8a/`。

> ✅ **这条路线的实测结果（2026-10-12 更新）**：借道 `android/arm64` 在官方 Go 上会被
> `net/cgo_resold.go:20` 的 `socklen_t` 类型冲突挡住（**无编译开关可解**），且还有 cgo TLS 墙。
> **项目最终走的不是这条路**，而是自建 `GOOS=openharmony` 的 Go 移植（在 Linux 上构建），
> 一次编过、零干预。产物已在真机验证。见 `docs/04`~`08`。
> **这段"借道"说明保留为历史记录**；`scripts/build-core.ps1` 的对应能力已不再是主路线。

单独验证 Go 代码本身（不需要 NDK）：

```powershell
cd entry/src/main/golang
go build ./... ; go vet ./...
```

> `connectServiceExtensionAbility` 会**静默断网**；内核跑在 UI 进程会被**后台冻结**；
> 隧道 MTU 1500 与上行网卡（1400）不匹配导致**下行近乎归零**。
> 详见 [`../TODO.md`](../TODO.md) §9。
>
> ⚠️ 模拟器仍然**不适用**：VPN 能力大概率不可用，且本机没有 `arm64-v8a` 镜像。
- 验证 `blockedApplications` 防环路是否生效（**验不到就会"连上即断网"**）
- 测速、分流、长时间挂机的稳定性

**模拟器基本不可用于上述验证**（VPN 扩展能力在模拟器上通常不可用 ❓，需以官方文档为准）。

## 8. 常见问题

| 症状 | 原因 | 处理 |
|---|---|---|
| `git status` 报 `failed in submodule .codegenie` | 历史上有一个无 `.gitmodules` 条目的幽灵 gitlink | 已在本仓库基线提交中修复；若在旧克隆上出现，`git rm --cached -f .codegenie` |
| sync 报找不到 SDK | `local.properties` 缺 `sdk.dir` | 用 DevEco 打开工程 sync 一次，或手写 §3.2 那行 |
| `hvigorw: 无法识别` | 不在 PATH | 用 §5.2 的全路径 |
| `ohpm: 无法识别` | 同上 | 用全路径 |
| `x86_64` 相关报错 | 内核只有 arm64 产物 | `entry/build-profile.json5` 的 `abiFilters` 只保留 `arm64-v8a` |
| NAPI 编译找不到 `napi/native_api.h` | NDK 路径未配置 | 由 hvigor 自动注入；命令行构建需确保 SDK 配置正确 |
