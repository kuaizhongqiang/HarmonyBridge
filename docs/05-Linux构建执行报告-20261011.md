## T1 · `libcore.so`

### 结论

| 路线 | 结论 | 干预次数 | 产物 |
| --- | --- | --- | --- |
| **A**（官方 Go + `GOOS=android`） | ✅ 编出 | **3 处**（见下） | `/home/kuai/opt/hb-runs/libcore-android-A.so`，33,042,640 B |
| **B**（fork + `GOOS=openharmony`） | ✅ 编出 | **0 处** | `/home/kuai/opt/hb-runs/libcore-ohos.so`，34,527,768 B |

两条路的 `go build` 参数与任务书 §4.1 一致：`-tags "fts5 timetzdata" -ldflags "-s -w" -buildmode=c-shared`。

### A 路线的真实失败链（原样粘贴，未润色）

**第 1 关 —— `android/log.h`（与任务书 §4.1 预测一致）：**

```text
# runtime/cgo
gcc_android.c:6:10: fatal error: 'android/log.h' file not found
```

**第 2 关 —— `socklen_t`（任务书 §4.2 问题 B，拦路石，原样粘贴）：**

```text
# net
/home/kuai/opt/go1.26.9/src/net/cgo_resold.go:20:76: cannot use _Ctype_size_t(len(b)) (value of uint64 type _Ctype_size_t) as _Ctype_socklen_t value in argument to (_C2func_getnameinfo)
```

**第 3 关 —— 链接期 `-llog`（任务书**没有**提到，A 路线的第三个障碍）：**

```text
# harmonybridge/core
/home/kuai/opt/go1.26.9/pkg/tool/linux_amd64/link: running .../llvm/bin/clang failed: exit status 1
ld.lld: error: unable to find library -llog
clang-15: error: linker command failed with exit code 1 (use -v to see invocation)
```
根因（✅ 已核实）：官方 Go 的 **android/arm64** 端口在链接期无条件追加 `-llog`（bionic 的 liblog），
而 OHOS sysroot 里没有 `liblog`，只有 `libhilog_ndk.z`。**加 `-lhilog_ndk.z` 不能替代**，因为
Go 的链接器是自己追加 `-llog` 的，不由 `CGO_LDFLAGS` 控制。

### 我为 A 路线做的三处改动（可复现）

1. **`android/log.h` shim**（任务书 §4.2 问题 A 给的方案）：
   `/home/kuai/opt/hb-runs/android-shim/android/log.h`，经 `CGO_CFLAGS` 注入 `-I`。

2. **Go 标准库补丁（A1 方案）**，产出可复现补丁文件
   `/home/kuai/opt/hb-runs/A1-socklen_t-cast.patch`：

   ```diff
   --- a/src/net/cgo_resold.go
   +++ b/src/net/cgo_resold.go
   @@ -17,6 +17,6 @@
    func cgoNameinfoPTR(b []byte, sa *C.struct_sockaddr, salen C.socklen_t) (int, error) {
   -	gerrno, err := C.getnameinfo(sa, salen, (*C.char)(unsafe.Pointer(&b[0])), C.size_t(len(b)), nil, 0, C.NI_NAMEREQD)
   +	gerrno, err := C.getnameinfo(sa, salen, (*C.char)(unsafe.Pointer(&b[0])), C.socklen_t(len(b)), nil, 0, C.NI_NAMEREQD)
    	return int(gerrno), err
    }
   ```
   **只改了 1 处**：`cgo_resold.go` 是目前构建里唯一把 `size_t` 传给 `socklen_t` 形参的点。

3. **绕开 `-llog`**：造一个**空静态库** `/home/kuai/opt/hb-runs/shim-libs/liblog.a`
   （`llvm-ar rcs liblog.a`，0 个成员），用 `CGO_LDFLAGS` 里的 `-L` 让它被解析到。
   空归档**不会**给产物加 `DT_NEEDED liblog.so`（🧪 产物 NEEDED 里确实没有 liblog），
   比伪造一个 stub `.so` 干净。

> ⚠️ A 路线的代价：这 3 处干预里，第 1 条和 Go 的 TLS 假设是同一条风险线
> （shim 同时定义了 Android 专用的 `x_cgo_inittls`），第 3 条是"让链接器以为有 liblog"。

### B 路线：一次编过，零干预 🧪

同一份源码、同一个 NDK，只把工具链换成 fork、`GOOS=android` 换成 `GOOS=openharmony`：

```bash
CC=$NDK/llvm/bin/clang  AR=$NDK/llvm/bin/llvm-ar
CFLAGS="-target aarch64-linux-ohos --sysroot=$NDK/sysroot -D__MUSL__"
CGO_ENABLED=1 GOOS=openharmony GOARCH=arm64 \
CGO_LDFLAGS="--target=aarch64-linux-ohos -fuse-ld=lld -lohcommonevent -lhilog_ndk.z -ltime_service_ndk" \
  /home/kuai/opt/ohos-go-src/bin/go build -tags "fts5 timetzdata" -ldflags "-s -w" \
  -buildmode=c-shared -o libcore.so .
```
→ `exit 0`，**没有出现 `socklen_t` 报错，也不需要 `android/log.h` shim、不需要 `-llog`**——
与任务书 §6.3 的判断完全一致（那两个障碍只属于 A 路线）。

**一处需要如实记录的新观察**（任务书未提）：fork 的 `GOOS=openharmony` 是**独立 GOOS**，
所以 xray-core 里 `//go:build linux` 的文件在 B 路线下**不会**被选中（A 路线选中的是 android 后端）。
本次**没有**出现编译错误（说明 xray-core 在这些点上不依赖 linux-only 文件），
但它意味着**两条路线的运行期行为不完全可比**：`runtime.GOOS` 也不同（fork 的
`zgoos_openharmony.go` 是 `const GOOS = "linux"`，而构建期 GOOS 是 `openharmony`）。❓ 真机行为未验证。

### ⭐ TLS 检查对比（任务书 §6.3 要的那份数据）

| | A 路线（官方 Go，`GOOS=android`） | B 路线（fork，`GOOS=openharmony`） |
| --- | --- | --- |
| `PT_TLS` 段 | **无** | **有**（`0x10` 字节） |
| TLS 动态重定位 | **无** | **1 条 `R_AARCH64_TLSDESC`** |
| 任务书判读 | 两者都不是"好消息"那条 —— 没有 `R_AARCH64_TLSDESC`，说明 TLS 访问没有走动态描述符 | **命中"好消息"**：`R_AARCH64_TLSDESC`，不是 `TLS_TPREL*` |

**工具链层面的解释（✅ 读源码核实，非推测）**：

- 官方 Go 1.26.9 的 `src/cmd/go/internal/work/init.go` 里**完全没有 `tlsModel` 这个变量**（🧪 `grep -c tlsModel` = 0）→ 不会强制任何 TLS 模型。
- fork 同文件第 218/246/266 行有 `tlsModel`，`c-shared` 分支第 262–266 行：
  `case "linux", "android", "freebsd", "openharmony":` → `case "arm64": tlsModel = "GD"`，
  第 367–368 行据此给汇编器强制 `-tls=GD -D=TLS_GD`。
- 这正好解释了上面两份产物的 TLS 差异：**B 路线强制广义动态 TLS（GD→TLSDESC），A 路线没有**。

> ❓ **仍未证实的**：`tlsModel = "GD"` 是**工具链级证据**，不是运行期证据。
> "外来线程（ArkTS / VPN 扩展）调 cgo 是否还会 SIGSEGV" 必须真机验证，本轮无法回答。

## T2 · `libhevsocks5tun.so`

### 结论：✅ 编出（一次通过，零干预），并额外定位到一个**交付缺口**

`bash scripts/build-tun2socks.sh $NDK` → `exit 0`。任务书 §7 的两个"仍未验证"项都已实测：

- ✅ `third-part/{lwip,yaml,hev-task-system}` **能**交叉编译到 OHOS musl（只有 `-fno-stack-clash-protection` 之类的 unused-argument 警告，无硬失败）。
- ✅ `-Werror` 未造成硬失败（脚本的 `-Wno-error` 生效）。
- ✅ 嵌套 submodule `src/core`（`1.6.4-5-ga5cc1a6`）确实被 `--recursive` 拉下来了。

**验收（脚本产物 `entry/libs/arm64-v8a/libhevsocks5tun.so`）：**

```text
file: ELF 64-bit LSB shared object, ARM aarch64, version 1 (SYSV), dynamically linked, with debug_info, not stripped
readelf -h: Class: ELF64  Type: DYN  Machine: AArch64
nm -D 三个 dlsym 目标（§7.2）：
  hev_socks5_tunnel_main_from_str   PRESENT

  hev_socks5_tunnel_stats           PRESENT
NEEDED: libyaml.so / liblwip.so / libhev-task-system.so / libc.so      ← ⚠️ 见下
```

### ⚠️ 新发现的交付缺口：脚本产物**不是自包含的**

`make shared` 依赖 `tp-shared`，把三个第三方库编成**独立 .so** 并写进 `DT_NEEDED`；
但 `build-tun2socks.sh` **只复制主库**到 `entry/libs/arm64-v8a/`。
→ 真机上 `dlopen("libhevsocks5tun.so")` 会因找不到 `libyaml.so` / `liblwip.so` /
`libhev-task-system.so` 而失败（**三个符号都在，但库加载不起来**）。

**我已实做一版自包含替代品**（未覆盖脚本产物，放在旁边待决策）：

```text
/home/kuai/opt/hb-runs/libhevsocks5tun-selfcontained.so   （286,736 B，stripped；strip 前 347,632 B）
file:   ELF 64-bit LSB shared object, ARM aarch64, ..., stripped
NEEDED: libc.so        ← 只剩这一个
nm -D:  hev_socks5_tunnel_main_from_str / _quit / _stats 三个都 PRESENT
```
做法：`make tp-static` 编出三个 `.a`，再用同一个 clang 手工重链，把
`libyaml.a` / `liblwip.a` / `libhev-task-system.a` 静态链进主库。
命令见本报告末尾"复现命令"。**这条改动属于"改配方"，按项目纪律需项目负责人拍板。**
