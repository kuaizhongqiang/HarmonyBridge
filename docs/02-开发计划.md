
> 🧪 阶段 B/C 的完成判据（2026-10-12）：`vpn-tun` 被创建、`libcore.so` 在**扩展进程**内运行、
> `libhevsocks5tun.so` 接管 vNIC fd、第三方应用可正常出网。
> **注意**：原来的判据里有 `Wired=true`，但那个字段在内核里是坏的（恒为 false），
> 正确判据是「`127.0.0.1:10808` 可连 + `vpn-tun` 双向计数增长」，
> 见 [`design/ipc-contract.md`](design/ipc-contract.md) §4.1。

**关键原则：阶段 B 必须与阶段 C 解耦。**
先用一个不转发任何流量的空壳 VPN 验证系统能力（授权弹窗、vNIC 创建、流量读数），
再去碰内核。否则一旦出问题，无法判断是平台能力还是内核集成的问题 —— 这是本项目最容易踩的坑。

## 3. 阶段 B：平台能力验证（✅ 已完成，🧪 真机 2026-10-12）

**目标：只证明系统能力，不做任何流量转发。**
这一步的产物是一个"空壳 VPN"，它是后续一切工作的地基。

> 🧪 **结果（HUAWEI `TYR-AL00` / API 24）**：
> B1 ✅（签名 HAP 安装并启动）；B2 ✅ 授权对话框出现（⚠️ `onAuthorizationResult` **运行时不存在**，
> 见下方 B2 行）；B3 ✅ 拿到 vNIC fd，状态栏出现 VPN 标识；B4 ✅ `vpn-tun` 有稳定读数；
> B5/B6/B7 ⏳ 未专门验证。
> **B3/B4 通过，因此不需要重新评估技术路线。**
>
> ⚠️ 本阶段的"空壳"形态**只是验证手段**：真正落地的 `VpnAbility` 会在建网卡后
> **在同一个扩展进程内**继续启动内核与数据面（见阶段 C）。

| # | 工作项 | 验收标准 |
|---|---|---|
| B1 | 编译出未签名 HAP 并在真机开发者模式安装 | 应用能启动，看到首页 |
| B2 | 触发 `startVpnExtensionAbility` | 系统授权对话框出现 ✅。⚠️ **`onAuthorizationResult` 拿不到结果**：`createVpnObserver` 在 `.d.ts` 里标 `@since 26.0.0`，真机运行时 `is not callable`。授权结果目前**没有回执通道** |
| B3 | `createVpnConnection` + `create(VpnConfig)` | 拿到 vNIC fd；系统状态栏出现 VPN 标识 |
| B4 | 观察 `vpn-tun` 接口 | `statistics.getIfaceTxBytes('vpn-tun')` 有稳定读数 |
| B5 | 验证授权被拒 / `2203001` 路径 | 有可理解的用户提示，不崩溃 |
| B6 | 长时间挂机 | 扩展进程存活策略明确，记录被回收的表现 |

## 4. 阶段 C：内核接入（✅ 已完成，🧪 真机 2026-10-12）

> 🧪 C1 ✅（`libcore.so` 34.5 MB，在 Linux 上编出）；C2 ✅（`26.3.27`）；
> C3 ✅（`127.0.0.1:10808` 可连、第三方应用能出网）；C4 ✅（内核出站源地址是蜂窝网卡地址，不是 tun 地址）；
> C5 ✅（`VPN_TRAFFIC` 事件回传，界面读数正确）；C6 ⏳ 未专门制造 panic 场景验证。
>
> ⚠️ **C4 的机制已升级为两层**：主手段是官方的 `protectProcessNet()`（`@since 22`，进程级、无需 fd），
> `blockedApplications` 作第二层兜底 —— 原方案只用后者，且当时把它的有效性标为 ❓。

| # | 工作项 | 验收标准 |
|---|---|---|
| C1 | 交叉编译 `libcore.so` | `scripts/build-core.*` 在 CI/本机产出 arm64 `.so` |
| C2 | 打通 `dlopen` + `dlsym` | `VersionService.GetVersion` 返回真实 Xray-core 版本 |
| C3 | vNIC fd → tun2socks → 本地 SOCKS | 最小配置（本地 socks 入站 + 单 vless 出站）能连通 |
| C4 | **`blockedApplications` 防环路** | 自身 egress 不回 TUN；把自身包名从名单里去掉应能复现环路 |
| C5 | `VPN_TRAFFIC` 回传 | 首页显示实时上下行速率与累计流量 |
| C6 | 崩溃防护 | 内核内部 panic 时应用不崩（信封返回错误） |

**出口条件**：C3 + C4 同时成立 —— 🧪 **2026-10-12 两项均已成立**。
环路防护机制已由 `protect(fd)` 换成 **`protectProcessNet()` + `blockedApplications` 两层**，
结论不变：**C4 失败等于"一连就断网"，不可发布**。
（`protect(fd)` 至今未用，因为它需要拿到内部 socket 的 fd，而 Go/hev 侧没有这样的 hook。）

## 5. 阶段 D：功能成型（⏳ 当前阶段）

> 下表的优先级**没有变**，但有几条已经部分完成，且有一条是**新发现的必需项**：
> - 「延迟测试」已实现，但它测的是**裸 TCP、不经代理**（`PingService.Tcping`），
>   且本应用在 `blockedApplications` 里 → **从应用内测域名验证不了隧道**。
>   要补一个"经 `127.0.0.1:<socksPort>` 的 SOCKS5 探测"（`TODO.md` §9.5）。
> - 「geoip/geosite 分流」**仍未完成**：`.dat` 至今没打包，rule 模式处在降级形态。
> - **新增必需项**：节点持久化、设置页接线、前台常驻通知与断线重连（`TODO.md` §9.5）。

按优先级排序（括号内为对齐 v2rayN 的能力）：

## 7. 风险登记与应对

| 风险 | 概率 | 影响 | 应对 |
|---|---|---|---|
| 真机授权/建 VPN 被拒 | 中 | **致命** | 阶段 B 最先验证；失败则改路线（如仅做规则生成器/订阅管理工具） |
| `GOOS=android` 借道在新版 Xray-core 失效 | 中 | 高 | 锁定版本；构建脚本做版本校验；预留 sing-box 备选 |
| Windows 宿主无法交叉编译 | 中 | 中 | 改用 Linux CI runner（Docker + NDK）交叉编译 |
| 内核崩溃拖垮 VPN 进程 | 中 | 高 | 强制 `recover`；信封返回错误；监控重建 |
| 回环未防住 → 一连就断网 | 中 | **致命** | C4 列为出口条件，必须显式验证 |
| HAP 体积过大（内核 32 MB + geo 数据 30 MB） | 高 | 中 | 按需下载 geo；剥离符号；评估功能裁剪 |
| 合规/上架政策不允许 | 中 | **致命** | 阶段 E 前置到"开工前"评估；见 `docs/research/03-合规与上架风险.md` |
| 许可冲突（GPL 传染） | 中 | 高 | 严守参考边界；决策前置 |

## 8. 每次迭代的完成定义（DoD）

1. 变更范围与写入路径明确，未越界修改。
2. 离线门禁全绿：`verify-repo.ps1`、`check-env.ps1`、Go 侧 `build`/`vet`、JSON5 校验。
3. 提交信息符合 Conventional Commits。
4. 若改动触及 C ABI 契约或 `module.json5`，四处/两处同步改完并说明。
5. 未提交任何构建产物、签名材料或密钥。
6. **如实标注验证状态**：没在真机上跑过就不能写"已验证"。
