# 02 · 开发计划

> 状态：计划稿。所有工期为**相对工作量**，不是日历承诺。
> 本阶段（无真机）的目标是"把可离线完成的准备工作做到位"，而非交付可用软件。

---

## 1. 总体策略

```
阶段 A  准备工作（当前，无真机）      → 仓库 / 文档 / 骨架 / 流水线 / 可行性
阶段 B  平台能力验证（需真机）        → 先证明"系统能力可用"，与内核解耦
阶段 C  内核接入（需真机）            → 把 vNIC fd 交给 tun2socks 跑通最小闭环（内核只做本地 SOCKS 入站）
阶段 D  功能成型（需真机）            → 订阅、节点、分流、日志、测速
阶段 E  打磨与决策（需真机 + 人）      → 许可决策、合规评估、签名、上架准备
```

**关键原则：阶段 B 必须与阶段 C 解耦。**
先用一个不转发任何流量的空壳 VPN 验证系统能力（授权弹窗、vNIC 创建、流量读数），
再去碰内核。否则一旦出问题，无法判断是平台能力还是内核集成的问题 —— 这是本项目最容易踩的坑。

## 3. 阶段 B：平台能力验证（需真机）

**目标：只证明系统能力，不做任何流量转发。**
这一步的产物是一个"空壳 VPN"，它是后续一切工作的地基。

| # | 工作项 | 验收标准 |
|---|---|---|
| B1 | 编译出未签名 HAP 并在真机开发者模式安装 | 应用能启动，看到首页 |
| B2 | 触发 `startVpnExtensionAbility` | 系统授权对话框出现；`onAuthorizationResult` 能拿到结果 |
| B3 | `createVpnConnection` + `create(VpnConfig)` | 拿到 vNIC fd；系统状态栏出现 VPN 标识 |
| B4 | 观察 `vpn-tun` 接口 | `statistics.getIfaceTxBytes('vpn-tun')` 有稳定读数 |
| B5 | 验证授权被拒 / `2203001` 路径 | 有可理解的用户提示，不崩溃 |
| B6 | 长时间挂机 | 扩展进程存活策略明确，记录被回收的表现 |
| B7 | 记录"扩展进程内不可用模块" | 与官方列出的 contact/geo/audio/camera/telephony 一致 |

**出口条件**：B2–B4 全部通过，且形成一份"平台能力实测报告"补进 `docs/research/`。
若 B3/B4 失败，**整个项目需要重新评估技术路线** —— 此时应停下并求助，而不是继续写上层代码。

---

## 4. 阶段 C：内核接入（需真机）

| # | 工作项 | 验收标准 |
|---|---|---|
| C1 | 交叉编译 `libcore.so` | `scripts/build-core.*` 在 CI/本机产出 arm64 `.so` |
| C2 | 打通 `dlopen` + `dlsym` | `VersionService.GetVersion` 返回真实 Xray-core 版本 |
| C3 | vNIC fd → tun2socks → 本地 SOCKS | 最小配置（本地 socks 入站 + 单 vless 出站）能连通 |
| C4 | **`blockedApplications` 防环路** | 自身 egress 不回 TUN；把自身包名从名单里去掉应能复现环路 |
| C5 | `VPN_TRAFFIC` 回传 | 首页显示实时上下行速率与累计流量 |
| C6 | 崩溃防护 | 内核内部 panic 时应用不崩（信封返回错误） |

**出口条件**：C3 + C4 同时成立。环路防护机制虽已由 `protect(fd)` 换成 `blockedApplications`，结论不变：**C4 失败等于"一连就断网"，不可发布。**

## 7. 风险登记与应对

| 风险 | 概率 | 影响 | 应对 |
|---|---|---|---|
| 真机授权/建 VPN 被拒 | 中 | **致命** | 阶段 B 最先验证；失败则改路线（如仅做规则生成器/订阅管理工具） |
| `GOOS=android` 借道在新版 Xray-core 失效 | 中 | 高 | 锁定版本；构建脚本做版本校验；预留 sing-box 备选 |
| Windows 宿主无法交叉编译 | 中 | 中 | 改用 Linux CI runner（Docker + NDK）交叉编译 |
| 内核崩溃拖垮 VPN 进程 | 中 | 高 | 强制 `recover`；信封返回错误；监控重建 |
| 回环未防住 → 一连就断网 | 中 | **致命** | C4 列为出口条件，必须显式验证 |
| HAP 体积过大（内核 32 MB + geo 数据 30 MB） | 高 | 中 | 按需下载 geo；剥离符号；评估功能裁剪 |
| 合规/上架政策不允许 | 中 | **致命** | 阶段 E 前置到"开工前"评估；见 `docs/research/03-合规与上架风险.md` |
| 许可冲突（GPL 传染） | 中 | 高 | 严守参考边界；决策前置 |

## 8. 每次迭代的完成定义（DoD）

1. 变更范围与写入路径明确，未越界修改。
2. 离线门禁全绿：`verify-repo.ps1`、`check-env.ps1`、Go 侧 `build`/`vet`、JSON5 校验。
3. 提交信息符合 Conventional Commits。
4. 若改动触及 C ABI 契约或 `module.json5`，四处/两处同步改完并说明。
5. 未提交任何构建产物、签名材料或密钥。
6. **如实标注验证状态**：没在真机上跑过就不能写"已验证"。
